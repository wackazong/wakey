# Pitfalls

Problems met on this board, their cause, and the fix in place. Read the entries for an area before changing it. Each entry: the symptom, why it happens, what the code does about it and where. Workarounds for upstream bugs that can go with a dependency update are also listed in [upgrades.md](upgrades.md).

## Platform and build

- **esp-hal does not run here.** It supports only ESP32-P4 rev ≥ v3.0; this Tab5 is rev v1.3. Hence ESP-IDF, which builds for rev < v3 with `CONFIG_ESP32P4_SELECTS_REV_LESS_V3`. Flash with ESP-IDF's bootloader (`scripts/flash.sh`), not espflash's bundled one.
- **`sdkconfig.defaults` changes rebuild much of ESP-IDF** (~10 min). Changes to `[package.metadata.esp-idf-sys]` in `Cargo.toml` may need `cargo clean --release -p esp-idf-sys`.
- **Only one nightly builds:** nightlies older than the pin ICE on esp-idf-svc's async `Wifi` impl (rust-lang/rust#164318); later ones cannot build `std` for `riscv32imafc-esp-espidf` at all (libc 0.2.191 renamed newlib's `stat` fields, rust-lang/rust#164555; fix pending in rust-lang/libc#5662). `rust-toolchain.toml` pins the one in between, nightly-2026-10-17; move it once a nightly has the libc fix and `cargo build --release --bins` passes.
- **Boot loop with `assert failed: esp_startup_start_app … (res == pdTRUE)`:** esp_hosted initialises in a C constructor and takes internal RAM before ESP-IDF creates the main task; a 64 KiB main task no longer fits. The executor runs on its own task (`runtime.rs`), the main task is 8 KiB, esp_hosted's pools and stacks are in PSRAM (`CONFIG_ESP_HOSTED_DFLT_TASK_FROM_SPIRAM`).
- **`AtomicU64` does not exist on the target** (`riscv32imafc`): use `AtomicU32` or a `Mutex`. `wakey-core` builds on the host, where it exists, so the error shows only in the firmware build.
- **The screen freezes while a computed tone plays:** the P4's FPU is single precision only; `f64` is soft-float, and `sinf` of a large argument (above ~200 rad) takes newlib's slow range reduction (`__kernel_rem_pio2f`). Per-sample `sin` and `%` used a whole core, and a priority-5 thread on core 0 starves the UI task (priority 1). The tone is a precomputed table (`wakey_core::tone`), and the decoder thread is pinned to core 1 (`audio/player.rs`). A task watchdog report naming `pthread` on CPU 0 with ROM math routines in the register dump points here.
- **The clock freezes 24 h after boot:** esp-idf-svc 0.53.0's embassy time driver arms the ESP-IDF timer with an overflowing timeout once the uptime passes one day and no timer is pending; the timer fires and re-arms itself in a loop on the `esp_timer` task. Signature: the task watchdog reports `IDLE0` with `CPU 0: esp_timer` every 5 s, register dumps in `esp_timer_start_once` and `schedule_next_expiration`, `ui-watch` reports the render loop stuck in `sleep`. Fixed in the vendored copy ([vendor/README.md](../firmware/vendor/README.md)). Anything that changes the time driver needs a run of more than 24 h to be trusted.
- **A second `EspDefaultNvsPartition::take()` fails:** the partition is taken once in `app::main` and cloned into `net::start` and the alarm.
- **Internal RAM runs out, then drivers and `std` fail:** with `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=16384` (every `malloc` up to 16 KiB tries internal RAM first), opening the alarm list took free internal RAM from ~87 KiB to ~10 KiB and DMA-capable memory to 0 (Slint's items, model rows, strings). Then the SD driver finds no buffer for one sector (`sdmmc_cmd: allocate_dma_buf: not enough mem`, `writing config.tmp: I/O error (os error 5)`), `std` cannot create a mutex (panic, abort), and frames run about four times slower (5 CPU cycles per instruction instead of 1.3). A larger `CONFIG_SPIRAM_MALLOC_RESERVE_INTERNAL` does not help: plain `malloc` uses up the reserve as well. `sdkconfig.defaults` sets it to 0: `malloc` takes PSRAM first. Where data sits is not the cause of the slowdown: a dependent load takes 6 cycles from internal RAM and from cached PSRAM alike; why frames slow down only while internal RAM is exhausted is not known. Watch the DMA figures in the per-second stats line.
- **Flashing interrupted by a short timeout** → "invalid segment length" and no bootable app. Writing the image takes ~30 s; allow ≥ 90 s when wrapping `cargo run` in a timeout.

## Display

- **The DSI PHY aborts in the HAL:** `phy_clk_src` must be 0 (the driver default) on rev < v3; the `…_DEFAULT` constant is the rev ≥ v3 choice.
- **Flicker in dark areas** (≈ 3 Hz, stronger when bright) with Espressif's BSP timings (70 MHz, 57.8 Hz). `display/mod.rs` uses M5GFX's: 80 MHz pixel clock, 66.1 Hz, 1040 Mbps lanes; the backlight PWM runs at 4 kHz (14 bits of duty, no flicker). esp-bsp's ST7123 table also declares `0xA3`/`0xE8` one byte too long (39 and 14 parameters are right; `display/init_tables.rs`).
- **The panel stays black after a new video stream** (frames run, DCS power mode 0x9c = on): after deleting and recreating the DPI panel, or changing its pixel clock, the whole link must be rebuilt as at boot: DSI bus, panel init (software reset, vendor table), then the stream (`Display::link_down`/`link_up`, ~0.45 s). Below 66 Hz (33 and 22 Hz tried) the panel shows nothing, but the ST7123's touch still scans, which display sleep uses.
- **Store access fault in `dpi_panel_init`** (`dw_gdma_ll_channel_set_link_list_master_port`, MTVAL 0x50081128) when the stream is recreated while the camera runs: `esp_lcd_panel_del` (ESP-IDF 5.5.5) does not stop the DPI's DW-GDMA channel, which keeps reading the freed frame buffers. Alone on the DW-GDMA nobody notices (the controller is switched off and reset with its last channel); with the camera's CSI receiver on it, the next stream gets the still running channel. `Display::stop_stream_dma` disables the channel (found by its source address) first. Fixed upstream (espressif/esp-idf#19437, see [upgrades.md](upgrades.md)).
- **Upside down or mirrored:** landscape `(x, y)` → panel column `y`, row `1279 − x`; touch is rotated 180° against display memory (`ui/input.rs`).
- **The PPA stalls for good** (no completion, no error) under DSI load when a rotated block is narrower than 8 output pixels, a block is wider than 640 px, or several transactions are queued. `display/ppa.rs` pads strips to ≥ 8 lines (`MIN_LINES`), splits wider blocks (`MAX_BLOCK_W`) and keeps one transaction in flight. The narrow-block stall is an ESP-IDF bug (espressif/esp-idf#19023). The PPA moves only ~20 Mpx/s; bulk copies go through the 2D-DMA (64 Mpx/s).
- **CPU writes into a PPA target are lost:** the driver invalidates the output rows before each transaction. The CPU never writes the frame buffer while the PPA is used.
- **`ESP_ERR_INVALID_ARG` from `ppa_do_scale_rotate_mirror`** ("out.buffer addr or out.buffer_size not aligned to cache line size"): the output buffer's address and size must be multiples of 128 bytes, which a picture made of an odd number of rows can miss. `psram::PsramBuffer` rounds allocations up to whole cache lines and `display/ppa.rs` passes the rounded size.
- **Frames flipped before their copy finished:** with one global 2D-DMA completion count shared by all users, one user's `wait` returns at once after another has made many copies. Each `FbCopy` counts its own completions (passed to the ISR as `cb_args`; `display/dma2d.rs`).
- **The clock crashes on waking from display sleep:** each display link rebuild (33 Hz asleep) frees the DPI panel's two frame buffers and allocates new ones; with ~2 MB of PSRAM free, the freed 3.7 MB come back as blocks too small for one (largest 1,835,008 of 1,843,200 bytes). Changing the pixel clock divider on the running link instead keeps the buffers but leaves the touch dead and the picture shifted. The DPI driver's buffer allocation goes through replaceable functions (vendored `esp_lcd`), and `display/mod.rs` keeps the first panel's two buffers for good (`FB_POOL`).
- **Panel sleep mode stops the touch:** the ST7123 is display and touch in one chip; after display off and sleep in (DCS 0x28, 0x10) it no longer reports touches, so a display put to sleep that way cannot be woken by a touch. Display sleep only switches the backlight off and lowers the frame rate (`ui::power`, `ui/render_loop.rs`); the panel keeps running.
- **The backlight barely dims with PWM:** on the Tab5 (ME2212 boost, PWM on its enable pin), 0.5 % is dark, 1 % is the dimmest visible level, and 2–40 % look the same; only above 40 % it gets visibly brighter. The same at 44.1 kHz, 25 kHz, 5 kHz, 1 kHz and 200 Hz (checked by eye with a labelled sweep; the INA226 sees nothing on USB power, as the backlight's current does not pass its battery shunt). The data sheet promises duty-proportional current from 100 Hz to 200 kHz; M5GFX drives it the same way. Night dimming therefore scales the pixels down (`ui::dim`) on top of the lowest backlight.

## Slint

- **Stutter every second:** Slint tracks at most 3 dirty rectangles by default; a ticking clock plus a scrolling list merge into full-screen repaints. Vendored `i-slint-core` allows 16; every independently changing text is its own fixed-width item.
- **Flicker in the list area at start:** Slint's first full repaints land over the list; the render loop composes the list again after Slint when their areas overlap (`FrameHook::overlaps`).
- **Flash size explodes with big fonts:** every imported face × every pixel size × ASCII is pre-rendered; two faces at 300 px overflow the app partition, and one new size (140 px) costs ~1.4 MB. One face per program, one compiled `.slint` file per program (pages are imported); reuse the sizes listed in `ui/wakey.slint`.
- **A second window component embeds every font again:** an `export component … inherits Window` for the list rows made the generated code hold every font size twice (5.65 → 8.64 MB). The offscreen rows are a second instance of `AppWindow` on a page of their own (`Page::AlarmListRow`, `Page::SoundListRow`).
- **Many dirty rectangles side by side are slow:** when several dirty items share the same lines (weekday chips, keyboard keys), Slint hands out one line range per rectangle, more than the PPA path keeps open strips (3); every strip is flushed after one line and padded from PSRAM. Seven chips took ~160 ms, a row of keys ~350 ms, against ~40 ms for a full-screen repaint. The vendored `DirtyRegion::add_box` merges a rectangle that shares lines with two or more others into one band. Still keep an edit's repaint to the items that change: no binding shared by a row of items (the chips own their state), no `for` over a model or array that changes (it re-creates its children; use `for i in N` with the changing value per item, as the keyboard does).
- **Rendering cost grows with items per line:** the line-by-line renderer visits every item on each line; the keyboard page (~30 items per line) is the slowest to repaint. The vendored renderer skips what lies behind an opaque rounded rectangle on its straight lines (cards, list rows): redrawing the alarm list 55 → 42 ms, a row 24 → 19 ms. A full-width list redrawn by Slint while scrolling is bound by the PPA's rotation rate (~21 Mpx/s, ~24 fps); the lists scroll on the list layer instead (DMA, 66 fps).
- **A binding on shared touch state repaints every row:** `highlighted: i == view.touched` in each row makes every row depend on `touched`, so a press, a swipe step or a toggle repaints the whole list. The alarm list's rows depend only on their alarm; an extra "active" row is drawn over the lit one with the touch state, and only it repaints. It is set only when it shows something and drawn only while needed (lit, or its highlight fading for 150 ms). The Rust side updates only rows that differ, which needs comparable rows: a `ModelRc` field compares by identity, so weekdays are a bit mask (`AlarmConfig::weekday_bits`), not a `[bool]` model.
- **Changes to an invisible item still repaint its area:** the hidden active row, moved to the touched row on every press, makes each scroll start with ~28 ms frames. It is moved only when it is about to show something, and back to -1 (outside the list) afterwards.
- **A reused row starts from stale values:** on the device Slint evaluates hidden items, so the active row's stale values (the previous alarm's switch state, an offset binding that treated "no active row" as open with both values -1) become the start of an animation: the row slides in at the first press. The binding tests `active >= 0`, and that row has `switch-animated: false`. The host preview does not show this; the bench's "first press" step checks it (the row repaints twice, both buffers, not for ~180 ms).
- **A component reused for several rows must not animate:** the list layer renders all rows with one offscreen component, right after setting each row's data; an animated switch is captured half-way from the previous row's state. `Row` and `Switch` have `animated`; `ListRowPage` sets it to false. `tools/ui-preview` compares every visible row of the page with the offscreen rendering pixel for pixel.
- **The other frame buffer lags one change behind:** Slint renders into the two buffers in turn and repaints only what changed since each was last drawn, but only when something asks for a redraw; the next touch's first frame then pays for it (60–70 ms). The render loop renders once more right after every Slint render. An empty render (the list layer requests one every frame) does not count, but still flips the buffers: Slint assumes one flip per render.
- **After a slide transition Slint owes one full repaint:** it rendered the new page into the transition's picture, believes one frame buffer holds it, and repaints that region in its next frame. The render loop does that catch-up right after the slide, where it costs nothing visible; left for later, the first touch on the new page takes ~60 ms.
- **Icons do not show on the device:** Slint's line-by-line renderer (`render_by_line`, what the firmware uses) skips every `Path` ("not supported in line-by-line mode"); the full-buffer renderer draws them, so a preview without `--by-line` shows icons the device would not. The vendored renderer rasterizes paths into an alpha map in line mode ([vendor/README.md](../firmware/vendor/README.md)); check icons with `--by-line`.
- **A button that changes the page on press hands its release to the new page:** the alarm line on the clock opens the list on touch, and the release would land on the list and open the alarm under it. The render loop drops the rest of a touch whose press requested a page change (`transition::pending`).
- **A font size passed through a property embeds no glyphs:** the software renderer embeds glyphs per font size it finds in `Text` items and does not follow a size given to a component (`Roll { font-size: 280px; }` into its `Text`); the text then draws at another, embedded size. The clock page has a hidden `Text` at 280 px with the digits; check new sizes in `tools/ui-preview`.
- **"Cannot override property" for `color`:** `Rectangle` already has `color` (an old name for `background`), so a component inheriting it cannot declare its own. `Roll` uses `text-color`.
- **`clip` ignores `border-radius`** in the software renderer: content is clipped to the rectangle and can show in the rounded corners. Round the content itself (the stop button's fill bar).
- **Wrong `default-font-family` embeds a second font:** with a name that matches no imported face (e.g. `"Inter 24pt"` for the family "Inter 24pt Medium"), the compiler embeds the system's sans-serif (Helvetica on a Mac) at every size, and the UI draws with it: capital umlauts without dots at 28–32 px, and 3.4 MB of flash. Use the exact family name; `tools/ui-preview` lists the embedded families in its generated code.
- **A `TouchArea` inside a moving element sees moving coordinates:** in a swipe-to-delete row a touch area that moves with the row makes `mouse-x` jump with every offset change. Put the touch area on the fixed parent and the sliding content above it.
- **Swipes on rows of a `Flickable` fail:** a swipe that drifts a little vertically is taken by the list (it intercepts after 8 px in a direction it can scroll). The list layer takes every touch that moves more than 12 px (the page gets a cancel through `WindowEvent::PointerExited`): mostly vertical it scrolls, sideways it swipes the row.
- **A swipe drawn by Slint lags behind the finger:** each step repaints the row (~20 ms per frame, plus the other buffer). The list layer draws swipes from pre-rendered pictures by 2D-DMA (~5 ms per frame). The content picture needs the red underlay square behind it (`ListRowPage`'s `underlay`), or its rounded corners show the page background as the row slides; near rest (moved less than the corner radius, `Layout::row_radius`) those red corners would show against the page, so the layer then draws the row from a plain picture.
- **`Flickable` holds a press back briefly** to tell taps from drags: a press, moves and a release within one frame (scripted touches) arrive as a tap. Scripted gestures (`app/bench.rs`) need ~16 ms between events.
- **Missing glyphs** for characters that only come from Rust strings (e.g. "März"): put them into a literal in the `.slint` file (the hidden `Text`s in `ui/wakey.slint`).

## Touch and I2C

- **A single tap cannot wake the chip from light sleep**, which is why the display sleeps and the chip does not. The ST7123 senses touches only while it receives the video stream (with the panel asleep or the link down: 0 scans), and light sleep stops the stream. Its Smart Wake Up mode (0x00F1 bit 7, panel display off and sleep in, then 0x0002 power down) keeps scanning and pulses `TP_INT` (0.3–6 ms) on a gesture: double tap (0x00F1 = 0x84), long press (bit 0); no gesture bit and no report shows a single tap. The pulse wakes the chip only with `gpio_sleep_sel_dis(23)` (the pin's sleep configuration switches its input off). After light sleep the DSI PHY's clock is gone: DCS commands stay in the command FIFO until the link is rebuilt. A double-tap wake from light sleep works this way and would save an estimated 0.1–0.2 W more ([roadmap.md](roadmap.md)).
- **`TP_INT` stays low until the report is read** (0x0010 up to the last coordinate): a level wake or sleep is refused while it is.
- **SDA held low after a reset** (a slave mid-byte): `SysI2c::new` clocks the bus free on every boot.
- **Touch lags, then stops, while touched quickly:** reads of the ST7123 time out (`ESP_ERR_TIMEOUT`, then NACKs) and the app looks hung. The legacy I2C driver sets the hardware's clock-stretch timeout to 2^10 clock cycles (~26 µs); the touch controller stretches SCL longer while it processes a touch. `board/i2c.rs` sets ~13 ms. As a safety net, the touch thread releases a held press when reads fail and pulses `TP_RST` after 5 failed reads within a second (`ui/input.rs`).
- **Drags break off:** the touch controller skips readings or times out mid-drag. A release needs 3 empty polls.
- **Flings have no speed:** polled as a task on the UI's executor, touch waits behind long frames (up to 90 ms between polls), and a fling measured from so few points has no speed. Touch is its own thread (`touch`, core 1, priority 6, `ui/input.rs`), events carry their read time.

## Built-in speaker

- **Silent until a power cycle:** clicks reach the I2S driver, the codec registers read back as written, `SPK_EN` is high, and still nothing sounds. Flashing only resets the P4; the ES8388 and the NS4150B stay powered (`SOC_3.3V`, `SYS_INT5V`) and can stay stuck. Unplug USB-C (no battery) before debugging silence. The codec init ends by restarting its state machine (register 2: `0xF0`, then `0x0A`, as Espressif's driver does), and register 24 says MCLK = 256 × fs, which is what the I2S driver sends (M5Unified's table says 128) (`board/codec.rs`).
- **Lone clicks come out cut off and faint:** with exact digital zeros between clicks (`auto_clear`), something in the chain mutes on digital silence and takes a moment to open again; clicks in fast succession keep it open. While the amplifier is on, the speaker thread streams ±2 LSB at half the sample rate (inaudible, filtered by the codec; `wakey_core::mix`), and the alarm page switches the amplifier on when it opens.
- **A 1 ms tick is barely audible alone, loud in a fast train:** the ear integrates energy over ~0.1–0.2 s. The click is ~10 ms in the mids, and quieter when it follows closely on the previous one (`tone::click`, `tone::click_gain`).

## USB audio

- **The Pebble clicks when USB-A's 5 V goes off or on** (its amplifier losing or getting power). Lowering the volume in steps or muting first does not help. Switching only the root port off (5 V on) avoids the click, but the Pebble then still draws ~80 mA, and ESP-IDF 5.5.5's USB host has no suspend. The firmware switches the 5 V and accepts the click.
- **"Root port reset failed" forever:** the HS controller must be full/low-speed only (`HCFG.FSLSSupp`, register 0x400 bit 2) after `usb_host_install` and before powering the port (`audio/uac/host.rs`). espressif/usb's `fsls_only` needs a newer ESP-IDF HAL than 5.5.5.
- **Order:** host installed with the root port unpowered, `USB5V_EN` on, 1 s for the speaker to boot, then port power. The first two resets still fail ("Root port reset failed" in the log is normal); the host stack recovers by itself, and the firmware cycles USB-A's 5 V if nothing enumerates within 3 s (`audio/uac/device.rs`).
- **Abort in `hub.c` when the root port is powered down during enumeration:** with `usb_host_lib_set_root_port_power(false)` the hub driver's state becomes `NOT_POWERED`; a disconnection then calls `dev_tree_node_dev_gone` for a device it never added ("Root port reset failed", `ESP_ERROR_CHECK failed … hub.c line 435`, abort; espressif/esp-idf#18366). The root port is powered once and never down; USB-A off and the enumeration retry switch only the 5 V, whose disconnections the hub driver handles in every state. Tested with USB-A switched at random intervals of 50–3000 ms: 245 changes, 76 enumerations, 165 failed resets handled, no abort.
- **Packets acknowledged, no sound:** ESP-IDF's interface claim does not send `SET_INTERFACE`; `audio/uac/device.rs` sends it explicitly.
- **Control IN transfers fail:** the buffer must hold the setup packet plus the data stage rounded up to 64 bytes.

## Memory and decoding

- **esp_hosted fails to start for lack of PSRAM** ("mempool create failed: no mem", assert in `sdio_mempool_create`): with `CONFIG_SPIRAM_XIP_FROM_PSRAM` the whole app image (code and constants) is copied into PSRAM at boot, so `include_bytes!` of the C6's images (2.2 MB) left 136 KiB after the first Wi-Fi session. Large data goes into a flash partition of its own (`c6`) and is read with `esp_partition_read` (`c6/ota.rs`).
- **Link error "--enable-non-contiguous-regions discards section …LAZY"** with symphonia 0.5: its FFT tables are inline statics (`lazy_static!` of `[Complex; N/2]` up to N = 65536: 256 KB for one), which fit no internal RAM region. symphonia 0.6 boxes them (heap, PSRAM); without default features, which pull in rustfft for SIMD.
- **"isomp4: no atom pending read" when a sound repeats:** symphonia 0.6.1's MP4 reader cannot seek back to 0 after its end. `AudioFile::rewind` (`wakey_core::audio_file`) opens the stream afresh.
- **Stack protection fault in `MediaSourceStream::refill_buffer`:** the decoder thread needs more than 8 KiB of stack for MP4/AAC. It has 64 KiB in PSRAM (the thread lives only while something plays).
- **A gap when an AAC sound repeats:** symphonia keeps the encoder delay (~2112 frames of silence at the start) and the last packet's padding at the end (~50 ms each at 44.1 kHz). Not handled.

## SD card

- **`send_op_cond` timeout:** the SD pins need on-chip LDO 4 at 3.3 V (`board/sd.rs`), and a card that is fully inserted.
- **No card: reboot loop as soon as the C6 talks** (`assert failed: xQueueSemaphoreTake queue.c (( pxQueue ))` from `hosted_sdio_card_init`, every ~5 s). The card (slot 0) and the C6 (slot 1) share the SDMMC controller, which esp_hosted initialises in a C constructor. When the card is missing, esp-idf-hal drops its `SdMmcHostDriver` and, counting itself as the only user, calls `sdmmc_host_deinit`: the whole controller goes, slot 1 and the transaction mutex included. `sd::restore_sdio_host` re-initialises the host and slot 1 from esp_hosted's sdkconfig values after a failed mount.
- **Long file names** need `CONFIG_FATFS_LFN_HEAP`; macOS `._*` files are skipped.
- **Card writes take half of a download:** `fwrite` from a PSRAM buffer that is not cache-line aligned goes through a small internal bounce buffer in pieces (SDMMC DMA needs 128-byte aligned PSRAM). `tidal/card_writer.rs` writes whole 32 KiB blocks from cache-line aligned PSRAM, and the card runs at 40 MHz (`speed_khz`; the default is 20).

## Wi-Fi (ESP32-C6)

- **The C6 never answers** (`sdmmc send_op_cond 0x107`): esp_hosted's Tab5 preset assumes an active-low reset and holds the C6 in reset. GPIO15 drives EN directly: `CONFIG_ESP_HOSTED_SDIO_RESET_ACTIVE_HIGH=y` (espressif/esp-hosted-mcu#258).
- **Host version:** esp_hosted host 2.x works with the factory C6 firmware (slave 1.4.1); 3.x is a different protocol. The factory firmware lacks transport-size reporting (warnings at start) and has a known RX stall under memory pressure (m5stack/M5Tab5-UserDemo#20); slave ≥ 2.13.1 fixes both. The firmware installs its own esp_hosted (2.13.1-wakey2, [`firmware/c6/`](../firmware/c6/README.md)).
- **The next session's driver start finds the C6 "unresponsive" and aborts:** dropping the Wi-Fi driver leaves esp_hosted's SDIO transport up, and a C6 switched off under it is not found again. The transport is `c6::Transport`: its drop calls `esp_hosted_deinit`, and the C6 is switched off only after it (`c6/mod.rs`, `net.rs`).
- **Each Wi-Fi session leaks ~2 KB internal RAM and ~29 KB PSRAM:** with `CONFIG_ESP_HOSTED_DFLT_TASK_FROM_SPIRAM`, esp_hosted creates its tasks static (stack in PSRAM, `StaticTask_t` in internal RAM), and `hosted_thread_cancel` deletes them without freeing either. `Transport`'s drop looks the buffers up (`hosted_task_buffers`, by task name, via `xTaskGetStaticBuffers`) before `esp_hosted_deinit` and frees them once the tasks are gone (`c6/mod.rs`). The free heap in the `wifi: session took …` log lines stays flat from one session to the next.
- **Peer data before the link is up goes unanswered:** after `esp_hosted_init` alone, a custom message gets no answer (RPC timeout), and `esp_hosted_deinit` with the SDIO card half set up asserts in `hosted_sdio_card_deinit` (free of a pointer outside the heap). In a Wi-Fi session the driver's start waits for the link; `c6::Transport` always calls `esp_hosted_connect_to_slave()` first, and its drop tears the transport down only if the link came up.
- **Telling a stock esp_hosted from Wakey's:** an esp_hosted without a handler for a message id answers the RPC with `ESP_ERR_NOT_FOUND`. The factory 1.4.1 instead fails the custom-data RPC (-1) and knows no OTA activate. `c6/peer.rs` reads the version first and treats anything below 2.13 as stock.
- **Updating the C6 over SDIO** (`c6/ota.rs`, `c6/mod.rs`): esp_hosted's slave OTA RPCs, no cable. 1.2 MB take ~12 s. Slaves before 2.6 switch at the OTA's end and do not answer `activate` (a 5 s timeout), so `c6/mod.rs` skips it for them (`ACTIVATE_MIN`); the SDIO errors when the C6 restarts are the old link going away. Build esp_hosted in DIO flash mode: QIO images of slaves 2.1–2.8 refuse later OTAs. The C6 has no rollback: an image that boots but does not talk SDIO needs the J1 header ([hardware.md](hardware.md)) or `firmware/c6/rescue`.
- **Building C6 images with the firmware's ESP-IDF:** its `export.sh` fails in `firmware/.embuild/espressif` (embuild installs only the tools the firmware needs); `firmware/c6/env.sh` sets the environment from what is installed.
- **The C6 carries a factory test SSID** ("M5Stack-Production"); harmless, the firmware sets its own configuration.
- **The C6's own output without a cable:** its IO2 is wired to the P4's GPIO14 (`RF_C6_IO2`); the receiver sends frames there by UART (`firmware/c6/airdrop/main/link.c`) and the P4 reads them (`airdrop.rs`). `CONFIG_ESP_CONSOLE_UART_TX_GPIO=2` alone does nothing: the bootloader routes the console pins, the app only sets the baud rate, and an image installed by esp_hosted's OTA runs under esp_hosted's bootloader (default pins, J1); the app has to set the pins itself.
- **A C6 image that crashes early leaves the C6 in a boot loop:** the C6's bootloader has no rollback, and the P4 can reset the C6 but not pull IO9 for download mode. An image installed by esp_hosted's OTA must point the boot slot back at esp_hosted (`esp_ota_set_boot_partition`) before anything can go wrong, so a power cycle restores the Wi-Fi firmware; the receiver does so first thing (its main task needs the stack for it: `esp_ota_set_boot_partition()` hashes the other image). The way back from a loop: bridge G9 to GND at header J1 and run `firmware/c6/rescue` on the P4, which resets the C6 into its ROM loader and rewrites esp_hosted over SDIO.
- **AWDL (AirDrop) on the C6 differs from the ESP32-S3** (`firmware/c6/airdrop`, ESP32Drop is written for the S3): the C6 is single-core (tasks pinned to core 1 assert). On the soft-AP interface its MAC does not ACK AWDL's unicast data frames (no ToDS/FromDS, the shared AWDL BSSID): 85 % arrive as 802.11 retries and the sender resets every TLS handshake; as an unassociated station it ACKs them. As a station its driver also transmits raw multicast data frames and reports their completion; a TX-done handler that returns early for multicast leaks one in-flight slot per frame until all transmission stops. The raw frames' rate (`esp_wifi_config_80211_tx`) takes 11b and 11g; an HT20 rate (MCS4) wedges the transmitter ("(tx)rts error … 0xab" for every frame until a reboot).
- **Downloads stall at ~180 KiB/s:** lwIP's default TCP window (5.7 KiB) and a 4 KiB HTTP buffer. `sdkconfig.defaults` sets a 256 KiB window with scaling (`CONFIG_LWIP_TCP_WND_DEFAULT`, `CONFIG_LWIP_WND_SCALE`, which needs `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP`) and larger receive mailboxes; `http::download` reads with a 16 KiB buffer.
- **A reused connection sends the previous request's headers:** ESP-IDF's HTTP client keeps `esp_http_client_set_header` values for its next request, so a resumed download's `Range` (or a token) goes out again. The vendored `esp-idf-svc` deletes the previous request's headers first ([vendor/README.md](../firmware/vendor/README.md)).
- **Download speed through the C6** (TIDAL, RSSI −56 dBm, 2.4 GHz, router at 20 MHz): the limit is the C6's radio link. esp_hosted's RawTP test carries ~75 Mbit/s from the C6 to the P4 over SDIO (`sdio_read` 13 % of a core), so bus and host are not it; 1, 2 or 4 connections at once give the same total; the round trip stays at ~7 ms during a download; a download on core 1 (core 0 then half idle) is as fast. **802.11ax costs ~25 %:** HE20 gives 1160 KiB/s, 802.11b/g/n (HT20) 1553 KiB/s, so `net::wifi_mode` disables ax. No effect: the C6 firmware (factory 1.4.1 or 2.13.1), longer esp_hosted queues, RX double buffering, Wi-Fi power saving, esp_hosted task stacks in internal RAM, 40 MHz channels. The C6's Wi-Fi buffers per Espressif's P4+C6 profile (`CONFIG_WIFI_RMT_*`, sent to the C6 with `esp_wifi_init`) give ~10 %.
- **Card writes slow the download:** the card and the C6 share the SDMMC controller, and ESP-IDF runs one transfer at a time over both slots (`s_request_mutex`). A 128 KiB card write holds the C6 off long enough to slow downloads by a fifth (1250 against 1560 KiB/s without the card); 32 KiB blocks give 1420 (16 KiB the same), hence `card_writer::BLOCK`.
- **AES-GCM costs ~60 % of core 0 at 1 MiB/s:** with mbedTLS's buffers in PSRAM, the hardware AES driver allocates alignment buffers and syncs caches per record, and GHASH (`gcm_mult`) runs in software; software AES is half as fast. `sdkconfig.defaults` enables ChaCha20-Poly1305 (`CONFIG_MBEDTLS_CHACHA*`), which mbedTLS offers first and which is cheaper.
- **Audio dropouts during a download:** the `wifi` thread (TLS) on core 1 next to the decoder at the same priority takes its time. It runs on core 1 at priority 1, below the decoder (5) and the card writer (4) (`net.rs`); on core 0 at the UI's priority it makes animations stutter.

## TIDAL

- **„not lossless (LOW)“ for some tracks:** with the device-login client, `playbackinfopostpaywall` answers every quality (LOW to HI_RES_LOSSLESS) for a track that has a Dolby Atmos mix with that mix: E-AC-3, 5.1, 48 kHz, ~770 kbit/s, `audioQuality` "LOW", `audioMode` "DOLBY_ATMOS". `immersiveaudio=false` gives the stereo FLAC (16 bit, 44.1 kHz, BTS). The browser-login (PKCE) client gets stereo anyway, but cannot do the device login („Client is not a Limited Input Device client“).
- **401 „Invalid access token without sessionId“** (subStatus 6004) from user calls: call `/v1/sessions` first (`tidal/session.rs`).

## Camera

- **Interrupt watchdog with the camera at 30 fps:** under heavy PSRAM load (TLS, SD card and display at once) the ISP's input FIFO can overflow, and ESP-IDF's ISP driver logs each overflow from its ISR (thousands per second). `ambient.rs` runs the sensor at 5 fps (frame length 7500 lines), disables the overflow interrupts after `esp_isp_enable` (ISP_INT_ENA 0x500A106C, bits 1 and 2), and drops a frame whose raw status shows an overflow (INT_RAW 0x500A1064, cleared through 0x500A1070). The trigger is not reproducible on demand; 5 fps is all a light meter needs.

## RTC

- **A fresh RX8130 can hold non-BCD junk with the power-loss flag clear.** `Rx8130::get_time` validates BCD and date ranges; `clock::init` also rejects times before the firmware build.

## Tools

- **`espflash monitor` resets the chip** when it connects (default `--before`); `--no-reset` only skips the reset afterwards. Listening without touching the chip: `espflash monitor -c esp32p4 --non-interactive --no-reset --before no-reset-no-sync`. It pauses ~9 s and warns "Secure Download Mode is enabled" (false: its loader commands time out against the running app; esp-rs/espflash#1130); the console is fine. After such passive sessions flashing can fail with "Timeout while running ReadReg" until the board is reset; `espflash flash --monitor` in one connection is reliable.
