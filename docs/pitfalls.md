# Pitfalls

Things that already went wrong on this board, with the fix that is in place. Read before changing the area; keep entries short.

## Platform and build

- **esp-hal does not run here.** It supports only ESP32-P4 rev ≥ v3.0; this Tab5 is rev v1.3. Hence ESP-IDF (which builds for rev < v3 with `CONFIG_ESP32P4_SELECTS_REV_LESS_V3`). Flash with ESP-IDF's bootloader (`scripts/flash.sh`), not espflash's bundled one.
- **`sdkconfig.defaults` changes rebuild much of ESP-IDF** (~10 min). Changes to `[package.metadata.esp-idf-sys]` in `Cargo.toml` may need `cargo clean --release -p esp-idf-sys`.
- **rustc ICE with Wi-Fi enabled:** nightly-2026-10-15 panics compiling esp-idf-svc's async `Wifi` impl for `AsyncWifi`. Vendored esp-idf-svc with that impl compiled out; use the blocking API.
- **Internal RAM before `main`:** esp_hosted initialises in a C constructor. With its defaults a 64 KiB main task no longer fitted: boot loop with `assert failed: esp_startup_start_app … (res == pdTRUE)`. The executor runs on its own task (`runtime.rs`), the main task is 8 KiB, esp_hosted's pools and stacks are in PSRAM.
- **No 64-bit atomics:** the target (`riscv32imafc`) has no `AtomicU64`; use `AtomicU32` (or a `Mutex`). `wakey-core` builds on the host, where it exists, so the error shows only in the firmware build.
- **Per-sample float math is slow:** the P4's FPU is single precision only; `f64` is soft-float, and `sinf` of a large argument (above ~200 rad) takes newlib's slow range reduction (`__kernel_rem_pio2f`). The built-in tone computed `sin` and `%` per sample and used a whole core; its thread (priority 5) starved the UI task (priority 1) whenever it ran on core 0: the screen froze while the tone played. The tone is now a precomputed table, and the decoder thread is pinned to core 1 (`ThreadSpawnConfiguration`). A task watchdog report naming `pthread` on CPU 0 with ROM math routines in the register dump points here.
- **`NVS` partition can be taken once:** `EspDefaultNvsPartition::take()` happens in `app` and is cloned into `net::start` and the alarm; a second `take()` fails.
- **Small allocations used up internal RAM:** with `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=16384` (every `malloc` up to 16 KiB tried internal RAM first), opening the alarm list took free internal RAM from ~87 KiB to ~10 KiB and DMA-capable memory to 0 (Slint's items, model rows, strings). Then the SD driver found no buffer for one sector (`sdmmc_cmd: allocate_dma_buf: not enough mem`, `writing config.tmp: I/O error (os error 5)`), so switching an alarm on or off was not saved; `std` could not create a mutex (panic, abort); and frames ran about four times slower (5 CPU cycles per instruction instead of 1.3, a list frame 130–170 ms instead of 42). A larger `CONFIG_SPIRAM_MALLOC_RESERVE_INTERNAL` (64 KiB) did not help: plain `malloc` used up the reserve as well. Now 0: `malloc` takes PSRAM first. Not the cause of the slowdown: where the data sits. A dependent load takes 6 cycles from internal RAM and from cached PSRAM alike, also while the list renders; why frames slow down only while internal RAM is exhausted is not known. Watch the DMA figures in the per-second stats line.
- **Flashing is interrupted by a short timeout** → "invalid segment length" and no bootable app. The 7 MB image takes ~30 s to write; allow ≥ 90 s when wrapping `cargo run` in a timeout.

## Display

- **DSI PHY clock:** `phy_clk_src` must be 0 (driver default) on rev < v3; the `…_DEFAULT` constant is the rev ≥ v3 choice and aborts in the HAL.
- **Flicker in dark areas** (≈ 3 Hz, stronger when bright) with Espressif's BSP timings (70 MHz, 57.8 Hz). Fixed with M5GFX's: 80 MHz pixel clock, 66.1 Hz, 1040 Mbps lanes, backlight PWM 44.1 kHz (now 4 kHz for 14 bits of duty; no flicker either). esp-bsp's ST7123 table also declares `0xA3`/`0xE8` one byte too long (39 and 14 parameters are right).
- **A new video stream alone leaves the panel black** (frames run, DCS power mode 0x9c = on): after deleting and recreating the DPI panel, or changing its pixel clock, the whole link must be rebuilt as at boot: DSI bus, panel init (software reset, vendor table), then the stream (`Display::link_down`/`link_up`, ~0.45 s). Below 66 Hz (33 and 22 Hz tried) the panel shows nothing, but the ST7123's touch still scans.
- **`esp_lcd_panel_del` does not stop the DPI's DW-GDMA channel** (ESP-IDF 5.5.5): it keeps reading the freed frame buffers. Alone on the DW-GDMA nobody notices (the controller is switched off and reset with its last channel); with the camera's CSI receiver on it, the next stream got the still running channel and `dpi_panel_init` died with a store access fault (`dw_gdma_ll_channel_set_link_list_master_port`, MTVAL 0x50081128). `Display::stop_stream_dma` disables the channel (found by its source address) first.
- **Frame buffers do not fit again after a rebuild:** in the app only ~6.5 MB of PSRAM are free and the largest block is often just short of one frame buffer; a rebuild succeeds only if nothing takes a piece of the freed buffers in between (ESP_ERR_NO_MEM on the fourth display sleep). `Display::suspend_stream` holds the memory with the driver's own allocation until the new stream allocates.
- **Upside down:** landscape `(x, y)` → panel column `y`, row `1279 − x`; touch is rotated 180° against display memory (`ui/input.rs`).
- **PPA stalls for good** (no completion, no error) under DSI load when: a rotated block is narrower than 8 output pixels (strips < 8 lines are padded), a block is wider than 640 px (split), or several transactions are queued (one in flight). The PPA moves only ~20 Mpx/s; bulk copies go through the 2D-DMA (64 Mpx/s).
- **CPU writes into a PPA target are lost:** the driver invalidates the output rows before each transaction. The CPU never writes the frame buffer while the PPA is used.

## Slint

- **Stutter every second:** with 3 dirty rectangles (Slint's default) a ticking clock plus a scrolling list merged into full-screen repaints. Vendored `i-slint-core` allows 16; every independently changing text is its own fixed-width item.
- **Flicker in the list area at start:** Slint's first full repaints land over the list; the render loop composes the list again after Slint when their areas overlap (`FrameHook::overlaps`).
- **Flash size explodes with big fonts:** every imported face × every pixel size × ASCII is pre-rendered. Two faces at 300 px overflowed the app partition. One face per program, one compiled `.slint` file per program (pages are imported). Each new size costs: adding 140 px (alarm page) grew `wakey` by 1.4 MB; reuse the sizes listed in `ui/wakey.slint`.
- **A second window component embeds every font again:** the alarm list's offscreen row was first its own `export component … inherits Window`; the generated code then held every font size twice and the image grew from 5.65 to 8.64 MB. The offscreen row is now a second instance of `AppWindow` on a page of its own (`page` 5, `ListRowPage`).
- **Many dirty rectangles side by side are slow:** when several dirty items share the same lines (weekday chips, keyboard keys), Slint hands out one line range per rectangle, more than the PPA path keeps open strips (3); every strip is flushed after one line and padded from PSRAM. Seven chips took ~160 ms, a row of keys ~350 ms, a full-screen repaint ~40 ms. The vendored `DirtyRegion::add_box` now merges a rectangle that shares lines with two or more others into one band. Still keep an edit's repaint to the items that change: no binding shared by a row of items (the chips own their state), no `for` over a model or array that changes (it re-creates its children; use `for i in N` with the changing value per item, as the keyboard does).
- **Rendering cost grows with items per line:** the line-by-line renderer visits every item on each line. The keyboard page (~30 items per line) took ~160 ms for a full repaint, other pages ~45 ms, measured while internal RAM was used up (see Platform), so today's numbers are lower. The vendored renderer skips what lies behind an opaque rounded rectangle on its straight lines (cards, list rows): redrawing the alarm list 55 → 42 ms, a row 24 → 19 ms. A full-width list redrawn by Slint while scrolling is bound by the PPA's rotation rate (~21 Mpx/s, ~24 fps); the alarm list scrolls on the list layer instead (DMA, 66 fps).
- **A binding on shared touch state repaints every row:** `highlighted: i == view.touched` in each row of the alarm list made every row depend on `touched`, so a press, a swipe step or a toggle repainted the whole list. The rows now depend only on their alarm; an extra "active" row is drawn over the lit one with the touch state, and only it repaints. It is set only when it shows something and drawn only while needed (lit, or its highlight fading for 150 ms): on top of its row it blends the rounded corners twice (≤ 8/255 at the corners). The Rust side updates only rows that differ, which needs comparable rows: a `ModelRc` field compares by identity, so weekdays are a bit mask (`AlarmConfig::weekday_bits`), not a `[bool]` model.
- **Changes to an invisible item still repaint its area:** the active row, hidden but moved to the touched row on every press, made each scroll start with ~28 ms frames (its area repainted, then again in the other buffer). It is now moved only when it is about to show something, and back to -1 (outside the list) afterwards.
- **A reused row starts from stale values:** the active row (one component showing whichever row is touched) slid in sideways at the first press after opening the list. Its offset binding treated "no active row" as open (`active == open-row` with both -1), and its switch slid from the previous alarm's state. On the device Slint evaluates hidden items, so the stale values became the start of an animation; the host preview did not show it, even rendering like the device. Fixed with `active >= 0` in the test and `switch-animated: false` for that row (a toggle hides it, so the switch slides in the real row). The bench's "first press" step checks it: the row repaints twice (both buffers), not for ~180 ms.
- **A component reused for several rows must not animate:** the list layer renders all rows with one offscreen row component, right after setting each row's data. Its switch animated from the previous row's state, so a switched-off row was captured half switched on. `Row` and `Switch` have `animated`; `ListRowPage` sets it to false. `tools/ui-preview` compares every visible row of the page with the offscreen rendering pixel for pixel.
- **The other frame buffer lagged one change behind:** Slint renders into the two buffers in turn and repaints only what changed since each was last drawn, but only when something asks for a redraw. After a page switch, the second buffer was brought up to date at the next touch, whose first frame took 60–70 ms. The render loop now renders once more right after every Slint render. An empty render (the list layer requests one every frame) does not count, but still flips the buffers: Slint assumes one flip per render.
- **Icons never showed on the device:** Slint's line-by-line renderer (`render_by_line`, what the firmware uses) skips every `Path` ("not supported in line-by-line mode"); the full-buffer renderer draws them, so a preview without `--by-line` showed icons the device never drew. The vendored renderer now rasterizes paths into an alpha map in line mode (see `firmware/vendor/README.md`); check icons with `--by-line`.
- **The 2D-DMA "done" counter was shared by all `FbCopy`s:** the list layer and the transitions each compared one global completion count with their own count of copies started. After the list layer had made many copies, the other instance's `wait` returned at once and a frame could be flipped before its copy finished. Each `FbCopy` now counts its own completions (passed to the ISR as `cb_args`).
- **After a slide transition Slint owes one full repaint:** it rendered the new page into a picture of the transition, believes one frame buffer holds it, and repaints that region in its next frame (it assumes the buffers alternate). Done right after the slide (the render loop's catch-up), it costs nothing visible; left for later, the first touch on the new page took 61 ms.
- **The PPA wants whole cache lines for its output:** `ppa_do_scale_rotate_mirror` fails with `ESP_ERR_INVALID_ARG` ("out.buffer addr or out.buffer_size not aligned to cache line size") unless the output buffer's address and size are multiples of 128 bytes. Picture sizes made of even row heights happened to fit; a third swipe picture slot made the size odd and the firmware panicked at the first swipe. Buffers are allocated rounded up to 128 bytes and `display/ppa.rs` passes the rounded size.
- **Powering the C6 off needs esp_hosted torn down first:** dropping the Wi-Fi driver leaves esp_hosted's SDIO transport up; with the C6 then switched off, the next session's driver start finds the slave "unresponsive" and aborts. `net::end_session` calls `esp_hosted_deinit` before `WLAN_PWR_EN` off, `session` calls `esp_hosted_init` before the driver. Each session still leaks ~2.3 KiB internal RAM and ~28 KiB PSRAM (measured over 5 sessions, scan only); harmless at one session a day for weeks, not forever (open). `esp_hosted_deinit` without the driver having connected asserts.
- **Panel sleep mode stops the touch:** the ST7123 is display and touch in one chip; after display off and sleep in (DCS 0x28, 0x10) it no longer reports touches, so a display put to sleep that way cannot be woken by a touch. The sleeping display only switches the backlight off (`ui::power`); the panel keeps running.
- **The backlight barely dims with PWM:** on the Tab5 (ME2212 boost, PWM on its enable pin), 0.5 % is dark, 1 % is the dimmest visible level, and 2–40 % look the same; only above 40 % it gets visibly brighter. The same at 44.1 kHz, 25 kHz, 5 kHz, 1 kHz and 200 Hz (checked by eye with a labelled sweep; the INA226 sees nothing on USB power: the backlight's current does not pass its battery shunt). The data sheet promises duty-proportional current from 100 Hz to 200 kHz. M5GFX drives it the same way (44.1 kHz, no offset). Night dimming therefore scales the pixels down to 35 % (`ui::dim`) on top of the lowest backlight.
- **A button that changes the page on press hands its release to the new page:** the alarm line on the clock opens the list on touch; the finger's release then landed on the list and opened the alarm under it (in the bench: clock → list → alarm in one frame, one "Forward" slide). The render loop now drops the rest of a touch whose press requested a page change (`transition::pending`).
- **A font size passed through a property embeds no glyphs:** the software renderer embeds glyphs per font size it finds in `Text` items, and does not follow a size given to a component (`Roll { font-size: 280px; }` into its `Text`). The clock's digits then drew at a size that was embedded (about a quarter as large). The clock page has a hidden `Text` at 280 px with the digits; check new sizes in `tools/ui-preview`.
- **`Rectangle` already has `color`** (an old name for `background`): a component inheriting it cannot declare its own `color` property ("Cannot override property"). `Roll` uses `text-color`.
- **`clip` ignores `border-radius`** in the software renderer: content is clipped to the rectangle and can show in the rounded corners. Round the content itself (the stop button's fill bar).
- **Wrong `default-font-family` embeds a second font:** with `"Inter 24pt"` (the file's family is "Inter 24pt Medium") the compiler found no match, embedded the system's sans-serif (Helvetica on the Mac that builds) at every size, and the UI drew with it. Symptoms: capital umlauts without dots at 28–32 px (the fallback face had no precomposed glyph there), and 3.4 MB of flash. Use the exact family name; `tools/ui-preview` lists the embedded families in its generated code.
- **A `TouchArea` inside a moving element sees moving coordinates:** in a swipe-to-delete row the touch area moved with the row, so `mouse-x` jumped with every offset change. Put the touch area on the fixed parent and the sliding content above it.
- **Scrolling list with swipeable rows:** with a `Flickable` and a touch area per row, a swipe that drifted a little vertically was taken by the list (it intercepts after 8 px in a direction it can scroll) and deleting failed once the list scrolled. In the alarm list the list layer takes every touch over that moves more than 12 px (the page gets a cancel through `WindowEvent::PointerExited`): mostly vertical it scrolls, sideways it swipes the row.
- **A swipe drawn by Slint lags behind the finger:** each step repainted the row (~20 ms per frame, plus the other buffer), so the row trailed the finger by a frame or two. The list layer now draws swipes from two pre-rendered pictures by 2D-DMA (~5 ms per frame). The content picture must have the red underlay square behind it (`ListRowPage`'s `underlay`), or its rounded corners show the page background as the row slides; the underlay picture is rendered without it. But near rest (moved less than the 28 px corner radius) those red corners show against the page: the layer then draws the row from a plain picture (or, unlit, from its ring slot).
- **`Flickable` holds a press back briefly** to tell taps from drags: a press, moves and a release within one frame (scripted touches) arrive as a tap. Real swipes are slower; scripted gestures need ~16 ms between events.
- **Missing glyphs** for characters that only come from Rust strings (e.g. "März"): put them into a literal in the `.slint` file.

## Touch and I2C

- **Touch wake from chip light sleep:** the ST7123 senses touches only while it receives the video stream (with the panel asleep or the link down: 0 scans), and light sleep stops the stream. Its Smart Wake Up mode (0x00F1 bit 7, panel display off and sleep in, then 0x0002 power down) keeps scanning and pulses `TP_INT` (0.3–6 ms) on a gesture: double tap (the firmware's 0x00F1 = 0x84), long press (bit 0); no gesture bit and no report shows a single tap. The pulse only wakes the chip with `gpio_sleep_sel_dis(23)` (the pin's sleep configuration switches its input off). After light sleep the DSI PHY's clock is gone: DCS commands stay in the command FIFO for good until the link is rebuilt. Spike `chip_sleep`.
- **`TP_INT` stays low until the report is read** (0x0010 up to the last coordinate): a level wake or sleep is refused while it is.

- **SDA held low after a reset** (a slave mid-byte): `SysI2c::new` clocks the bus free on every boot.
- **Touch lagged, then stopped, while touched quickly:** reads of the ST7123 timed out (`ESP_ERR_TIMEOUT`, then NACKs) and the app looked hung. The legacy I2C driver sets the hardware's clock-stretch timeout to 2^10 clock cycles (~26 µs); the touch controller stretches SCL longer while it processes a touch. `SysI2c::new` sets ~13 ms. As a safety net, the touch task releases a held press when reads fail and pulses `TP_RST` after 5 failed reads within a second.
- **Drags broke off** because the touch controller skips readings or times out mid-drag: a release needs 3 empty polls.

## Built-in speaker

- **Silent until a power cycle:** the wheel clicks stopped; every tick reached the I2S driver, the codec registers read back as written, `SPK_EN` was high, and even the last firmware that had clicked was silent. Unplugging USB-C (no battery) brought the sound back. Flashing only resets the P4; the ES8388 and the NS4150B stay powered (`SOC_3.3V`, `SYS_INT5V`) and can stay stuck. Power-cycle before debugging silence. The codec init now ends by restarting its state machine (register 2: `0xF0`, then `0x0A`, as Espressif's driver does), and register 24 says MCLK = 256 × fs, which is what the I2S driver sends (M5Unified's table said 128).
- **Lone clicks came out cut off and faint:** between clicks the stream was exact digital zeros (`auto_clear`), and something in the chain mutes on digital silence and takes a moment to open again; clicks in fast succession kept it open. While the amplifier is on, the click thread now streams ±2 LSB at half the sample rate (inaudible, filtered by the codec) instead, and the alarm page switches the amplifier on when it opens.
- **A 1 ms tick was barely audible alone, loud in a fast train:** the ear integrates energy over ~0.1–0.2 s. The click is now ~15 ms in the mids, and quieter when it follows closely on the previous one.

## USB audio

- **The Pebble clicks when USB-A 5 V goes off or on** (its amplifier losing or getting power). Lowering the volume in steps and muting it first did not help. Switching only the root port off (5 V on) avoids the click, but the Pebble then still draws ~80 mA; ESP-IDF 5.5.5's USB host has no suspend. Kept: 5 V off, with the click.

- **"Root port reset failed" forever:** the HS controller must be full/low-speed only (`HCFG.FSLSSupp`, register 0x400 bit 2) after `usb_host_install` and before powering the port. espressif/usb's `fsls_only` needs a newer ESP-IDF HAL than 5.5.5.
- **Order:** host installed with the root port unpowered, `USB5V_EN` on, 1 s for the speaker to boot, then port power. The first two resets still fail ("Root port reset failed" in the log is normal); the host stack recovers by itself, and the firmware power-cycles the port if nothing enumerates within 3 s.
- **Packets acknowledged, no sound:** ESP-IDF's interface claim does not send `SET_INTERFACE`; send it explicitly.
- **Control IN transfers:** the buffer must hold the setup packet plus the data stage rounded up to 64 bytes.

## SD card

- **`send_op_cond` timeout:** the SD pins need on-chip LDO 4 at 3.3 V — and a card that is fully inserted (that was the actual cause once).
- Long file names need `CONFIG_FATFS_LFN_HEAP`; macOS `._*` files are skipped.
- **Card writes took half of a download:** `fwrite` from a PSRAM buffer that is not cache-line aligned goes through a small internal bounce buffer in pieces (SDMMC DMA needs 128-byte aligned PSRAM). Write whole blocks (32 KiB, see the SDMMC entry under Wi-Fi) from `heap_caps_aligned_alloc(128, …)` buffers, and run the card at 40 MHz (`speed_khz`; the default is 20).

## Wi-Fi (ESP32-C6)

- **C6 never answers** (`sdmmc send_op_cond 0x107`): esp_hosted's Tab5 preset assumes an active-low reset and holds the C6 in reset. GPIO15 drives EN directly: `CONFIG_ESP_HOSTED_SDIO_RESET_ACTIVE_HIGH=y`.
- **Host version:** esp_hosted host 2.x works with the factory C6 firmware (slave 1.4.1); 3.x is a different protocol. This unit's C6 now runs slave 2.13.1 (feature `c6-update`, see below). The factory firmware lacks transport-size reporting (warnings at start) and has a known RX stall under memory pressure (m5stack/M5Tab5-UserDemo#20); updating the C6 to slave ≥ 2.13.1 would fix both.
- **Updating the C6** (feature `c6-update`, `firmware/src/c6_update.rs`): esp_hosted's slave OTA RPCs over SDIO, no cable. The image is esp_hosted's `slave` project from the host component (`managed_components/espressif__esp_hosted/slave`, same version), built for the C6 with the project's ESP-IDF in `firmware/.embuild/espressif`: its `export.sh` fails (embuild installs only the tools the firmware needs), so set `IDF_PATH`, `IDF_TOOLS_PATH`, `IDF_PYTHON_ENV_PATH`, `ESP_IDF_VERSION=5.5` and `PATH` (python env, `riscv32-esp-elf`, cmake, ninja) by hand, then `python $IDF_PATH/tools/idf.py set-target esp32c6 build` (DIO flash mode; QIO images of slave 2.1–2.8 refuse later OTAs). The image in the repo: `firmware/c6/` (procedure there). 1.2 MB take ~12 s; slaves before 2.6 switch at `end` and do not answer `activate` (a 5 s timeout, harmless); the P4 restarts, and the SDIO errors just before are the old link going away. The C6 has no rollback: an image that boots but does not talk SDIO needs the J1 header (`docs/hardware.md`).
- The C6 carries a factory test SSID ("M5Stack-Production"); harmless, the firmware sets its own configuration.

- **Downloads stalled at ~180 KiB/s:** lwIP's default TCP window (5.7 KiB) and a 4 KiB HTTP buffer. `CONFIG_LWIP_TCP_WND_DEFAULT=65534`, larger receive mailboxes, 16 KiB read buffer; 256 KiB with window scaling (`CONFIG_LWIP_WND_SCALE`, which needs `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP`) gave another ~15 %.
- **Download speed through the C6** (TIDAL, RSSI −56 dBm, 2.4 GHz channel 5, router at 20 MHz): the limit is the C6's radio link. Measured (features `download-bench`, `netbench.rs`): esp_hosted's RawTP test carries ~75 Mbit/s from the C6 to the P4 over SDIO (`sdio_read` 13 % of a core), so bus and host are not it; 1, 2 or 4 connections at once give the same total; the round trip stays at ~7 ms during a download; a download on core 1 (core 0 then half idle) is as fast. **802.11ax costs ~25 %:** HE20 gave 1160 KiB/s, 802.11b/g/n (HT20) 1553 KiB/s (`net::wifi_mode`). Not it: the C6 firmware (factory 1.4.1 and 2.13.1 the same), longer esp_hosted queues, RX double buffering, Wi-Fi power saving, esp_hosted task stacks in internal RAM, 40 MHz (the router stays at 20 MHz). The C6's Wi-Fi buffers per Espressif's P4+C6 profile (`CONFIG_WIFI_RMT_*`, sent to the C6 with `esp_wifi_init`): ~10 %.
- **The card and the C6 share the SDMMC controller:** ESP-IDF runs one transfer at a time over both slots (`s_request_mutex`). A 128 KiB card write held the C6 off long enough to slow downloads by a fifth (1250 against 1560 KiB/s without the card); 32 KiB blocks: 1420 (16 KiB: the same).
- **AES-GCM cost ~60 % of core 0 at 1 MiB/s:** with mbedTLS's buffers in PSRAM, the hardware AES driver allocates alignment buffers and syncs caches per record, and GHASH (`gcm_mult`) runs in software; software AES was half as fast. ChaCha20-Poly1305 (`CONFIG_MBEDTLS_CHACHA*`) is cheaper. In profiles, time with interrupts off shows up as `vPortExitCriticalMultiCore`; `scripts/profile.sh … profile-ra` lists its callers (mostly queue and heap locks here).
- **Audio dropouts during a download:** the `wifi` thread (TLS) ran on core 1 next to the decoder at the same priority. Pinned to core 0 at priority 1.

## TIDAL

- **„not lossless (LOW)“ for some tracks:** with the device-login client, `playbackinfopostpaywall` answers every quality (LOW to HI_RES_LOSSLESS) for a track that has a Dolby Atmos mix with that mix: E-AC-3, 5.1, 48 kHz, ~770 kbit/s, `audioQuality` "LOW", `audioMode` "DOLBY_ATMOS". `immersiveaudio=false` gives the stereo FLAC (16 bit, 44.1 kHz, BTS). The browser-login (PKCE) client gets stereo anyway; it cannot do the device login („Client is not a Limited Input Device client“).
- **401 „Invalid access token without sessionId“** (subStatus 6004) from user calls: call `/v1/sessions` first.

## Camera

- **Interrupt watchdog during downloads:** at 30 fps the ISP's input FIFO overflowed while TLS, the SD card and the display all used PSRAM, and ESP-IDF's ISP driver logged each overflow from its ISR (thousands per second). The sensor now runs at 5 fps (frame length 7500 lines), the overflow interrupts are disabled after `esp_isp_enable` (ISP_INT_ENA 0x500A106C, bits 1 and 2), and a frame whose raw status shows an overflow is dropped (INT_RAW 0x500A1064, cleared through 0x500A1070).

## RTC

- A fresh RX8130 can hold **non-BCD junk with the power-loss flag clear**. `get_time` validates BCD and date ranges; `clock::init` also rejects times before the firmware build.

## Tools

- **`espflash monitor` puts the chip into download mode** when it connects (default `--before`: DTR/RTS); `--no-reset` only skips the reset afterwards. Listening without touching the chip: `espflash monitor -c esp32p4 --non-interactive --no-reset --before no-reset-no-sync`. After such passive sessions flashing sometimes failed with "Timeout while running ReadReg" until the board was reset; `espflash flash --monitor` in one connection was reliable.
