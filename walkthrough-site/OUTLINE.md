## The architecture as I understand it

**The device.** A bedside alarm clock on the M5Stack Tab5: ESP32-P4 (two RISC-V cores, 32 MB PSRAM), a 1280×720 touch panel, microSD, a USB speaker or the built-in one, and an ESP32-C6 as radio co-processor. Rust `std` on ESP-IDF 5.5.5, so FreeRTOS, `std::thread`, `std::sync` and `std::fs` are all there.

**Two crates.** `wakey-core` is pure logic without ESP dependencies, tested on the host: the alarm state machine, the config model, date and time, texts, scroll physics, audio file readers, the TIDAL and AirDrop protocols. `firmware` (library crate `wakey`, binaries `wakey` and `ui_bench`) is everything that touches hardware.

**Four layers in the firmware**, none using a layer above it (`lib.rs`): `app` (the only place that knows the product) → services (`ui`, `audio`, `net`, `tidal`, `http`, `airdrop`, `sounds`, `clock`, `config`, `ambient`) → hardware (`board`, `display`, `c6`) → support (`runtime`, `psram`, `taskstats`). Services get what they need as arguments: a `Switch` closure instead of the IO expander, a callback instead of the RTC, plain `fn() -> bool` instead of the UI.

**Concurrency: one Embassy task, many threads.** This is the finding that shapes the walkthrough. `runtime::start` spawns a 64 KiB FreeRTOS task `app`, puts an `embassy_executor::Executor` in a `StaticCell` and runs it. The executor has exactly one task in the product, `app::app` (`ui_bench` and the `ui-bench` feature add a second). That task brings the board up, wires everything and ends in `render_loop::run(...).await`, which never returns. The `await` points that matter are `display.back_buffer().await` (woken by the frame-complete ISR through `HalIsrNotification`), `select(Timer::after(..), input::EVENTS.receive())` when idle, and the slide transitions. Everything else that runs concurrently is a named `std` thread spawned through the `runtime::Thread` builder: `touch`, `usb-lib`, `uac`, `decoder`, `speaker`, `wifi`, `card-writer`, `cover`, `ambient`, `ui-watch`, optionally `task-stats`. Each one's doc comment says why it is a thread and why it has its core and priority. The walkthrough explains Embassy and its executor from this real use, and is explicit that the code chose threads for most work and why.

**Board resources.** `Board::init()` calls `Peripherals::take()` once and returns a struct of owned handles. `app` destructures it and moves each handle to the one service that owns it from then on: `display` to the render loop, `backlight` to the `ambient` thread, `modem` and `c6_link` to the `wifi` thread, `codec` to the `speaker` thread, `rtc` into the NTP callback. Three things are shared, each differently: the I2C bus as `Arc<Mutex<SysI2c>>` locked per transaction, the IO expanders as a `Clone` handle over `Arc<Mutex<(Image, Image)>>`, and single expander pins as boxed `Switch` closures.

**Communication.** Six mechanisms, each used where it fits: an `embassy_sync::Channel` (touch thread → render loop, the only thread → async crossing), `std::sync::mpsc` (commands to `uac`, `speaker`, `wifi`, `card-writer`), atomics in statics (`ui::power`, `ui::dim`, `ambient`, `airdrop::WANTED`, `tidal::EDITING`, render-loop stage), `Arc<Mutex<..>>` behind `Clone` handles (`Wifi::status`, `Tidal::inner`), `Mutex` + `Condvar` (the player's ring, TIDAL's `kick`, the C6 peer reply), and closures handed downwards (`Source`, `Switch`, `Job`, `on_time_synced`). ISRs end in an atomic or a `HalIsrNotification`.

**State.** UI-thread state is single-threaded and lives in `Rc<Ctx>` with `RefCell` fields (the `AlarmClock`, the draft being edited, the original for change detection, the name being typed), captured by Slint callbacks through `Ctx::with*`. `AlarmClock` owns the config list, the pure `wakey_core::alarm::Alarms` machine, and the handles that make the speaker follow it; `follow()` is the single place where a state change becomes NVS writes and sound. What survives a reboot is in two stores: `config.json` on the card (settings, rewritten under a static `Mutex`) and NVS (the alarm phase and done-days as JSON). Slint globals are a projection of that state, written only where a value changed. Cross-thread state is the atomics and handles above.

**Input and output.** In: touch (polled over I2C every 10 ms), the camera as a light meter, the RTC, the INA226, UART frames from the C6, HTTP. Out: the panel through Slint → 16-line strips → PPA rotation → back buffer → flip, list scrolling and slides by 2D-DMA, the backlight PWM, two speakers, `config.json` and NVS.

**Errors.** Four deliberate policies: panic with the chip's name for hardware the clock cannot run without; `Result` with `EspError`, `io::Error` or `anyhow::Error` inside a layer; typed reports across layers (`net::Unavailable`, `tidal::Problem`, `airdrop::State`) that `app/texts.rs` turns into words; and log-and-continue for everything optional. A broken `config.json` gets its own page and stops the clock on purpose. Poisoned locks are taken anyway (`unwrap_or_else(|e| e.into_inner())`).

**`unsafe`.** 135 occurrences in 25 files, none in `wakey-core` or `app/`. They fall into a few classes, each with a `// SAFETY:` comment (`clippy::undocumented_unsafe_blocks` is on, `unsafe_op_in_unsafe_fn` denied): plain FFI calls, zeroed C config structs, `extern "C"` callbacks and ISRs, `#[unsafe(no_mangle)]` hooks into the vendored `esp_lcd`, raw PSRAM buffers and slices over them, one `unsafe impl Send`, peripheral reborrows, one `static mut` register.

## Platform decisions

- **Zola 0.23.6**, installed with Homebrew (not on this machine yet) and pinned in the README. Templates follow the 0.23 documentation.
- **Code excerpts** are shortcode bodies in the Markdown with `file`, `lines` and `hl` arguments. A script (`scripts/excerpt`) pastes them from `git show 0fdbf78:<file>`, and `scripts/verify-excerpts` checks every excerpt against that commit; `// ...` markers may stand for skipped lines inside the stated range. No excerpt is typed by hand.
- **Mermaid** is self-hosted and loaded only on pages that have a diagram, themed from the site's CSS variables for light and dark. SVGs use the same variables.
- **Fonts** are self-hosted; no request leaves the site. All URLs go through `get_url`, so any base URL works.
- **Reading time** is computed in the templates from Zola's word count at the walkthrough's `wpm` (front matter, 155 here), per chapter and summed for the overview and the landing card.
- A second walkthrough is one new folder under `content/` with an `_index.md`; the README ships a skeleton to copy.

## Candidates for `NOTES.md`

Seen so far, each to be confirmed against the code before it goes in:

- `input::EVENTS.try_send` drops an event silently when the 32-slot channel is full; a dropped `Up` would leave Slint with a pressed pointer.
- `Player::start` polls `is_playing()` in a 10 ms sleep loop on the calling (UI) thread while the previous decoder stops.
